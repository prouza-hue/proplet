# 4.09.6 — personal team victories and return celebration

Production audit on 18 October: rewards enabled; active hourly minute-10 cron;
closed weeks 28 Sep–4 Oct (n², 25,780 XP) and 5–11 Oct (Kupkovi, 27,155 XP).
Seven frozen recipients: three acknowledged, four pending. No production writes
were made for the audit or preview.

An existing unacknowledged team award can now celebrate on Dnes, Hrát, Já or
Pořadí. It waits while playing, hidden, in first-steps quiet mode or behind another
modal. Existing once/account acknowledgement, team awards and scoring stay intact.

The profile shows personal team wins immediately after its statistics. The new
authenticated, read-only `/api/team-victories/personal` reads the existing frozen
recipient ledger. A new teammate cannot inherit past wins; seen and unseen awards
remain visible, including after leaving/changing a team. The detail lists the
winning week, the team name at that time, team XP and shared-first status. Personal
milestones use 1/3/10/25 personal wins and further Legend levels every 25. The
shared team cabinet retains its own totals.

No schema migration, historical reward update or XP grant. The new read is lazy
on the profile with a five-minute account-scoped in-memory cache, request
deduplication, retry and stale-identity protection. The query has a hard 5,000-row
bound that fails closed instead of returning a truncated total; the UI displays
the latest 100 awards while its count includes all returned awards. A normal week
adds at most one personal win.

Coordinated 4.09.6 release/cache markers and changed asset revisions preserve all
player progress, account keys and content caches. Historical API digests remain
unchanged after explicitly checking/removing only the new GET route.

Preview builds generate `/design/team-rewards/?teamRewards=victory` (or `profile`,
`no-team`) using the native shell and existing isolated archive API adapter. All
fixture identities and acknowledgements are local. Production builds omit the
review page and strip the archive adapter as before.

Verification is wired into the current runtime manifest (HTTP and frontend
regressions) and weekly workflow (existing real SQL gate plus native-shell browser
coverage). Local HTTP and frontend checks pass; CI/browser outcomes are recorded
in the PR after completion. Production deployment requires preview approval.
